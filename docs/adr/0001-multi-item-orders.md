# ADR 0001: Заказ из нескольких позиций

- **Дата:** 2026-06-16 · **Статус:** Accepted

## Задача

На шаге 4.1 проектируем схему заказа. План предполагает корзину из нескольких товаров,
а уже написанный inventory-service (Этап 3, тесты зелёные) построен под **одну позицию
на событие** — Avro-схема `OrderCreated` несёт ровно один `productId` и `quantity`.

Либо упрощаем модель под готовый код, либо переделываем уже закрытый сервис.

## Что решили

Заказ — из нескольких позиций: одна запись `orders` + N строк `order_items`. Avro-схемы
`OrderCreated` и `InventoryReserved` переезжают на список позиций. Цена фиксируется
снимком в `order_items.unit_price` на момент оформления — потом каталог может её менять,
на уже оформленный заказ это не влияет.

Схемы меняем **не сейчас, а перед шагом 4.4**, когда order-service впервые опубликует
`order.created`. Смысл в том, чтобы править схему до первой реальной публикации: после
неё в Schema Registry появится зарегистрированная версия, и любое изменение придётся
делать совместимым.

## Почему не иначе

Одна позиция на заказ проще в реализации, но это не магазин, а витрина с кнопкой
«купить один товар». Для портфолио корзина — минимальное ожидание.

## Чем платим

- Переделкой закрытого inventory-service: два Avro-файла, цикл по позициям в консьюмере,
  правка интеграционного теста. gRPC- и unit-тесты не задеты.
- Всплывает вопрос атомарности: резерв заказа из N позиций должен быть «всё или ничего» —
  решается на 4.4 в `InventoryTxOperations`.
- Outbox даёт at-least-once, поэтому потребители обязаны быть идемпотентными
  (доделано в [ADR 0021](0021-outbox-concurrency-and-reserve-idempotency.md)).
