# ADR 0002: Один продьюсер Outbox на все типы событий

- **Дата:** 2026-06-25 · **Статус:** Accepted

## Задача

До шага 4.5 order-service публиковал из outbox ровно один тип события — `OrderCreated`.
Поллер был жёстко типизирован: `KafkaTemplate<String, OrderCreated>` и маппер под эту
единственную схему.

Компенсация (шаг 4.5) добавляет второй тип, `OrderStatusChanged`. Сама таблица outbox
к этому готова — в ней есть `event_type`, `topic` и `payload` в JSON, — а продьюсер знает
только одну схему. Надо решить, как поллер публикует произвольное число разных схем.

## Что решили

Один продьюсер на общего предка всех Avro-классов — `KafkaTemplate<String, SpecificRecord>`.

Это работает, потому что `KafkaAvroSerializer` берёт схему **из самого объекта** и
регистрирует её в Schema Registry под именем топика. Конкретный Java-тип ему не нужен.

Выбор «какой класс собрать из payload» делается по полю `event_type` в `OutboxAvroMapper`.
У `switch` есть ветка по умолчанию: неизвестный тип бросает исключение → транзакция
поллера откатывается → `published_at` не проставляется → событие уедет на следующем тике.
Событие не теряется и не проглатывается молча.

Заодно развели обязанности: фабрика собирает запись в outbox, маппер разбирает её в Avro,
поллер занимается только механикой «прочитал пачку — отправил — пометил».

## Почему не иначе

Отдельный `KafkaTemplate` на каждый тип события — дублирование, растущее линейно.
К моменту `PAID`/`SHIPPED`/`COMPLETED` таких блоков было бы уже пять.

## Чем платим

- Типобезопасность теряется: соответствие «тип события → Avro-класс» проверяется в рантайме.
  Прикрыто веткой по умолчанию и юнит-тестами.
- Настройки продьюсера общие для всех топиков. Если понадобятся разные `acks` или
  партиционер — придётся разделять обратно.
