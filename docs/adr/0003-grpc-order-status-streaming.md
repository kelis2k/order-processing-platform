# ADR 0003: Стрим статусов заказа — на Reactor Sinks в памяти

- **Дата:** 2026-06-27 · **Статус:** Accepted

## Задача

Шаг 4.7 добавляет server-streaming `StreamOrderStatus(orderId)`: клиент подписывается
и получает смены статуса в реальном времени. Откуда стрим берёт обновления — вопрос
открытый, в ТЗ этого нет.

Важное наблюдение: источник правды находится **внутри самого order-service**. Все переходы
идут через единственный метод `transition()` — и при создании заказа, и в саговых реакциях.
Узнавать об изменениях откуда-то извне не требуется.

## Что решили

Обновления идут через `Sinks.Many` из Reactor — шину в памяти процесса. Одна шина на все
заказы, фильтрация по `orderId` происходит у подписчика, реестр «заказ → канал» не нужен.

Ключевая деталь — **публикация после коммита, а не внутри транзакции**. `transition()`
шлёт доменное событие, а слушатель с `AFTER_COMMIT` кладёт его в шину. Иначе клиент мог бы
получить `RESERVED` по заказу, который после отката транзакции так и остался `NEW`.

При подключении клиент сначала получает текущий статус из БД, потом подписывается на шину.
Поток закрывается сам на терминальном статусе; отвалившийся клиент освобождает подписку.

## Почему не иначе

- **Опрос БД из стрима** — это не push, а его имитация: постоянные `SELECT` на каждое
  соединение и задержка, равная интервалу опроса.
- **Kafka-консьюмер на каждый стрим** — оверкилл: динамические группы, офсеты, отсев чужих
  заказов. Плюс на тот момент `order.status-changed` публиковался только при отмене.

## Чем платим

- **Работает в пределах одного экземпляра.** Если стрим висит на реплике A, а статус сменила
  реплика B, клиент A ничего не увидит. Для локального стенда неактуально; при
  масштабировании лечится гибридом «локальный Sink + Redis Pub/Sub», gRPC-слой при этом
  не меняется.
- Статус и время идут строками, без protobuf-enum и Timestamp — простота вместо
  типобезопасности на проводе.
