# ADR 0004: Вход через Google и GitHub — одна личность на email

- **Дата:** 2026-07-03 · **Статус:** Accepted

## Задача

Шаг 5.3 добавляет вход через внешних провайдеров поверх обычного входа по паролю.
Spring Security сам проводит redirect-обмен с провайдером, но на выходе даёт **чужую**
личность. Нам нужен свой пользователь в базе auth-service и свой JWT — иначе всё, что
построено дальше, придётся учить второму способу аутентификации.

Три вопроса без очевидного ответа: как сопоставить внешнюю личность с локальной, как
ужиться сессионному OAuth-контуру со stateless-контуром `/auth/**`, и что вернуть клиенту
после входа, если фронта нет и редиректить некуда.

## Что решили

**Личность определяется по email.** Нашёлся пользователь с таким адресом — используем его
как есть, в том числе если он заводился паролем. Не нашёлся — создаём: `enabled = true`
(провайдер email уже проверил), пароля нет, роль обычная, и в той же транзакции через
Outbox уходит `user.created`. Поля «каким провайдером заведён» существующему пользователю
не переписываем — они описательные, а не ключ.

**Две цепочки фильтров.** Первая обслуживает `/oauth2/**` и держит сессию — она нужна для
`state` и `nonce`. Вторая — прежний stateless-контур для `/auth/**`, его не трогаем.

**Токен отдаётся JSON'ом, а не редиректом.** Свой обработчик успеха достаёт атрибуты
провайдера, зовёт доменный метод и пишет в ответ те же access и refresh, что и обычный
вход. Заодно снимается вопрос отсутствующего фронта: демо в браузере показывает токены
прямо в теле ответа.

## Почему не иначе

Строгая пара «провайдер + идентификатор в нём» как ключ личности потребовала бы снять
уникальность email и допускала бы три аккаунта на один адрес — локальный, Google и GitHub.
Для учебного стенда это сложность без пользы.

## Чем платим

- **Риск угона аккаунта.** Кто-то регистрирует неподтверждённый локальный аккаунт на чужой
  email, жертва входит через Google — и попадает в аккаунт атакующего. Смягчено тем, что
  локальный вход до подтверждения почты заблокирован; принято осознанно.
- **Краевой случай:** если по email найден неподтверждённый локальный пользователь, соцвход
  выдаст ему токен, хотя обычный вход вернул бы 403. Не стали трогать найденную сущность.
- **У GitHub email может быть скрыт** — базовый профиль отдаёт `null`. Пришлось дописать
  сервис, который дочитывает адреса отдельным запросом и берёт основной подтверждённый.
- Сессия OAuth-цепочки живёт в памяти экземпляра: при масштабировании понадобится общее
  хранилище сессий.
