# ADR 0005: Ролью владеет user-service, а в токен её кладёт auth

- **Дата:** 2026-07-03 · **Статус:** Accepted

## Задача

По ТЗ роли (`ROLE_USER`, `ROLE_MANAGER`, `ROLE_ADMIN`) — забота user-service. Но JWT
выпускает auth-service, а сервисы дальше по цепочке проверяют доступ **по роли из токена**,
не обращаясь ни к базе, ни к соседям.

Отсюда разрыв: владелец роли и тот, кто печатает её в токен, — разные сервисы. ТЗ мост
между ними не описывает. Причём до этого шага auth хранил роль сам и де-факто был её
владельцем, что требованию противоречило.

## Что решили

**Истина о роли живёт в user-service.** Смена роли идёт через его эндпоинт `PUT /users/{id}/role`.

**auth-service превращается в реплику.** Он ставит роль по умолчанию при регистрации — это
нужно, чтобы выдать первый токен, не дожидаясь создания профиля. Все последующие изменения
он получает **только** событием `user.role-changed`, которое user-service публикует через
тот же Outbox, что и остальные события. При следующем входе актуальная роль попадает в токен.

Событие `user.created` при этом не меняется: роль по умолчанию оба сервиса знают
самостоятельно, и связывать их на пути регистрации незачем.

## Почему не иначе

- **Оставить истину в auth** — просто и токен всегда актуален, но требование ТЗ выполняется
  только на бумаге: настоящим владельцем RBAC остаётся auth.
- **Спрашивать роль у user-service при каждом входе** — буквально по ТЗ, но кладёт
  user-service на критический путь: он недоступен — вход не работает.
- **Не класть роль в токен вообще**, спрашивать при каждом запросе — убивает stateless-модель
  и делает user-service единой точкой отказа для всей платформы.

## Чем платим

- **Лаг актуализации.** Уже выданный токен живёт 15 минут со старой ролью. Для повышения
  прав безвредно, для понижения — окно, в котором старые права ещё действуют. Это
  фундаментальное свойство stateless JWT; мгновенный отзыв потребовал бы чёрного списка.
- **Два писателя в поле роли у auth** — регистрация и консьюмер. Разведены по времени:
  регистрация только для нового аккаунта, дальше пишет только консьюмер.
- **Первого администратора выдать некому** — все регистрируются обычными пользователями.
  Решено сидом по адресу из `ADMIN_EMAIL` при обработке `user.created`.
- Между сменой роли и обновлением реплики — задержка Kafka и поллера, обычно доли секунды.
