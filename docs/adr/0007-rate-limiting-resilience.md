# ADR 0007: Свой rate-limiter — при отказе Redis деградация, а не тишина

- **Дата:** 2026-07-13 · **Статус:** Accepted

## Задача

Шаг 6.2 добавляет ограничение частоты запросов в шлюз. Алгоритм — token bucket, состояние
вёдер в Redis, а не в памяти: при нескольких репликах шлюза локальное хранение дало бы
пользователю по отдельному лимиту на каждую. Lua-скрипт обеспечивает атомарность —
иначе две реплики одновременно спишут последний токен.

Цена такого решения в том, что **Redis оказывается на пути каждого запроса**. Что делать,
если он недоступен — рестарт, сетевой сбой, переключение мастера?

Разбор байт-кода коробочного `RedisRateLimiter` (Spring Cloud Gateway 4.2.1) дал
неприятный ответ: при **любой** ошибке Redis он пишет строчку в лог и возвращает
«разрешено». Флага «отклонять при отказе» нет вообще. То есть ограничение выключается
целиком и незаметно — ровно тогда, когда система уже нездорова.

## Что решили

Написан свой лимитер, который переиспользует готовый Lua-скрипт SCG, но ошибками
управляет сам:

- **таймаут 100 мс** — защита от «Redis жив, но подвис»: лимитер не имеет права быть
  медленнее того, что он защищает;
- при ошибке или таймауте решение принимает **локальное ведро в памяти** (Caffeine) —
  тот же алгоритм, только per-instance;
- каждый такой случай увеличивает счётчик `gateway.ratelimit.degraded`, то есть
  деградация **видна метрикой**, а не спрятана в ERROR-логе.

Обёрткой над стандартным лимитером обойтись было нельзя: он глотает ошибки внутри себя
и наружу всегда отдаёт успешный ответ — перехватывать нечего.

**Ключ гибридный:** `user:<sub>` для аутентифицированных, `ip:<addr>` для анонимных.
Тонкость: у анонимного токена `isAuthenticated()` возвращает `true`, и без явной проверки
все анонимы схлопнулись бы в одно общее ведро.

**Лимиты свои на каждый маршрут:** `/auth` — 1 запрос в секунду при ведре 5 (анти-брутфорс),
`/products` — 20 (дешёвое чтение), `/orders` — 5 (запись и SAGA), `/users` — 10.

## Почему не иначе

- **Принять коробочное поведение** — ноль кода, но лимита нет ровно тогда, когда он нужен.
- **Отклонять запросы при отказе Redis** — лимит соблюдён ценой полного отказа шлюза:
  падение вспомогательного кэша роняет бизнес-функциональность.
- **HA-Redis** проблему не снимает: во время выборов нового мастера команды всё равно
  падают. Политика на случай ошибки нужна при любой топологии.

## Чем платим

- **Локальное ведро действует в пределах реплики:** при четырёх шлюзах в режиме деградации
  эффективный порог вчетверо выше. Неточный лимит лучше отсутствующего.
- Зависимость от внутреннего API Spring Cloud Gateway — при мажорном обновлении код может
  потребовать правки. Прикрыто юнит-тестами: поломка проявится в CI.
- В режиме деградации WARN пишется на каждый запрос — при долгом отказе Redis возможен
  лог-шторм.
- IP берётся из адреса соединения, а не из `X-Forwarded-For`: доверять заголовку без
  доверенного прокси — значит позволить клиенту подделать свой IP и обойти лимит.

Проверено вживую: `docker stop redis` — шторм по `/auth/login` продолжает получать `429`,
счётчик деградаций растёт.

## Не путать

другая задача и **противоположное** решение по отказу Redis.
