# ADR 0009: Событие о статусе заказа стало самодостаточным

- **Дата:** 2026-07-14 · **Статус:** Accepted

## Задача

Шаг 6.4 добавляет notification-service — первого потребителя `order.status-changed`.
Появление потребителя вскрыло **два дефекта контракта**, незаметных, пока событие никто
не читал.

**Событие не позволяло сделать работу.** Оно несло идентификатор заказа, статус, причину и
время — и всё. Email лежит в `user.created`, связка «заказ → пользователь» — в `order.created`.
Получив «заказ X отменён», сервис уведомлений физически **не знал, кому писать**.

**Топик был наполовину пуст.** Запись в outbox стояла внутри ветки компенсации, поэтому в
Kafka уходил только `CANCELLED`. Переход в `RESERVED` жил лишь во внутренней шине для
gRPC-стрима. То есть gRPC-клиент видел `RESERVED`, а уведомления — нет, и топик
`order.status-changed` фактически был `order.cancelled`.

## Что решили

**Событие несёт `userId`.** Владелец — законная часть заказа, а не «чужие данные»: событие
о заказе, не называющее владельца, просто неполное. Это обычный event-carried state transfer:
потребитель не бегает за данными, всё нужное приехало в сообщении.

Поле добавлено **со значением по умолчанию** — иначе Schema Registry не зарегистрировал бы
новую версию: в топике уже лежат сообщения без этого поля, и старый формат должен остаться
читаемым.

**Событие рождается в `transition()`**, а не в ветке саги. Теперь метод в одной транзакции
делает три вещи: проверяет допустимость перехода, меняет статус и пишет в outbox. Правило
«прошёл переход → событие ушло» сформулировано один раз, и забыть его при добавлении новых
статусов физически нельзя.

Порядок внутри метода не случаен: в outbox пишем **внутри** транзакции (иначе событие
потеряется), а внутреннюю шину дёргаем **после коммита** (иначе клиент увидит статус,
которого после отката не существует).

**Идемпотентность потребителя — уникальным индексом, а не проверкой перед вставкой.**
В MongoDB стоит составной уникальный индекс «тип письма + заказ + статус», вставка идёт
через `insert`, повторная доставка ловится исключением о дубликате.

Проверка «существует ли уже» перед вставкой была бы **TOCTOU**: между проверкой и записью
есть окно, а при ребалансировке группы одно сообщение может обрабатываться двумя
консьюмерами сразу. Атомарность «проверить и вставить» есть только у базы.

**Неизвестный получатель — исключение, а не пропуск.** Если `user.created` ещё не доехал,
консьюмер падает и сообщение перечитывается с нарастающей паузой. Честнее, чем молча
потерять письмо.

## Почему не иначе

Можно было не трогать схему, а построить в notification-service вторую проекцию
«заказ → пользователь» из `order.created`. Отвергнуто: сервис уведомлений по ТЗ ни от кого
не зависит, а так он получил бы состояние, живущее на гонке двух топиков.

## Чем платим

- Старые сообщения в топике читаются с пустым `userId` — получателя нет, письмо не уйдёт.
  Для dev неважно, в проде понадобился бы backfill.
- Событий стало больше: теперь публикуется каждый переход. Для уведомлений это плюс, для
  будущих потребителей — нагрузка, которой не было.
- Ретраи при неизвестном получателе останавливают партицию; отдельной очереди для «мёртвых»
  сообщений не заведено.
