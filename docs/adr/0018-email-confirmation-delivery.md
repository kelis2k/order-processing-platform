# ADR 0018: Ссылка подтверждения — отдельным топиком

- **Дата:** 2026-07-30 · **Статус:** Accepted

## Задача

С шага 5.2 регистрация создаёт пользователя выключенным и кладёт одноразовый токен в базу.
Эндпоинт подтверждения этот токен принимает. **Но до пользователя токен не доходил** — письма
со ссылкой не существовало, в коде на его месте стояла запись в лог.

Поэтому во всех ручных прогонах подтверждение делалось запросом в чужую базу:

```bash
docker exec postgres-auth psql -c "UPDATE users SET enabled = true WHERE ..."
```

Это нарушает database-per-service и оставляет критерий ТЗ «жизненный цикл без ручных вмешательств»
выполненным только на бумаге. Плюс демо-скрипт без этого самодостаточным быть не может.

## Что решили

**Новый топик `user.confirmation-requested`** со своей схемой и единственным потребителем.
auth-service публикует событие **через Outbox** — в одной транзакции с созданием пользователя
и токена. notification-service добавляет консьюмер и тип письма, шаблон лежит строкой в MongoDB,
как остальные.

**Ссылка строится из `APP_PUBLIC_URL`.** Без явной настройки в письмо уехал бы внутренний адрес
контейнера, по которому пользователь никуда не попадёт.

**Появился `GET /auth/confirm?token=`** — из письма ссылку кликают, а не отправляют POST. Прежний
POST остался для программных клиентов.

## Почему не иначе

- **Положить токен в существующее `user.created`** дешевле всего, но этот топик читают **двое**,
  и второму потребителю токен не нужен. Одноразовый пропуск не стоит размазывать по подписчикам.
- **Отправлять письмо прямо из auth-service** нарушило бы правило «письма шлёт только
  notification-service» и продублировало бы и SMTP-настройки, и ограничение частоты.

## Чем платим

- Плюс топик, схема и тип письма — движущихся частей больше.
- **Токен уезжает в Kafka открытым текстом.** Для dev приемлемо; в проде правильнее публиковать
  только идентификатор и забирать токен по защищённому каналу.
- **Ограничение частоты писем распространяется и на подтверждения:** при превышении лимита письмо
  получит статус `SUPPRESSED`, и пользователь не сможет подтвердить регистрацию. В проде такие
  письма стоило бы вынести из общего ведра.

## Важная деталь реализации

Письмо-подтверждение **не использует проекцию получателей** — адрес и имя берутся прямо из события.
Причина в гонке: два топика обрабатываются независимо, и ожидание проекции давало бы «получатель
неизвестен» и лишние ретраи. Та же логика, что в [ADR 0009](0009-self-contained-order-status-changed.md):
событие должно быть самодостаточным. Закреплено отдельным тестом.
