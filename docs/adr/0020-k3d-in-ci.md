# ADR 0020: Helm-релиз в CI — настоящий кластер, а не `helm lint`

- **Дата:** 2026-07-31 · **Статус:** Accepted

## Задача

Шаг 10.1.C должен закрыть строку ТЗ «Helm-release в dev-namespace». Постоянного кластера у проекта
нет и не предполагается, значит «dev» в CI может быть только эфемерным — создаётся внутри прогона
и умирает вместе с раннером.

Плюс чарт требует от кластера шесть секретов, которые локально приезжают через sealed-secrets.

## Что решили

**Поднимать настоящий k3d прямо в раннере** и ставить umbrella-чарт с ожиданием готовности подов
и откатом при неудаче.

**Обычные Secret вместо sealed-secrets — иначе никак.** Контроллер sealed-secrets генерирует пару
ключей **при установке в конкретный кластер**. Кластер в CI новый каждый прогон, значит ключ новый,
и шифротексты из репозитория он расшифровать **не может**.

Причина глубже технической: sealed-secrets решают задачу «секрет лежит в git и при этом безопасен».
В CI секрет в git не лежит — он рождается внутри прогона, живёт десять минут и умирает вместе
с кластером. Шифровать нечего и не от кого. Локальный `make k3d-up` остаётся на sealed-secrets и
продолжает проверять этот механизм.

**Деплой только при push в `main`.** На pull request остаётся быстрый контур примерно на девять
минут; полный прогон с кластером занимает 20–25.

**Откат при неудаче — вместе с диагностикой до него.** `--atomic` удаляет ресурсы неудавшегося
релиза, а вместе с ними логи упавших подов. Поэтому шаги сбора состояния стоят **перед** откатом
и выгружают события, описания и логи артефактом. Логи берутся с флагом «предыдущий запуск» — при
`CrashLoopBackOff` интересны именно они, текущий контейнер ещё ничего не написал.

## Почему не иначе

`helm lint` и рендер шаблонов проверяют синтаксис YAML, но не поймают ни `ImagePullBackOff`, ни
отсутствующий Secret, ни под, который стартует и падает. И тогда следующему шагу — интеграционным
тестам по стенду — просто негде выполняться.

## Чем платим

- Прогон вырастает с девяти до двадцати с лишним минут.
- Появляется класс падений, не связанных с кодом: таймауты, сбои при загрузке образов.
- Пути в CI и локально разошлись: там обычные Secret, здесь sealed-secrets. Принято сознательно.

## Следствие для защиты ветки

Job, который не запускается на pull request, **нельзя** делать обязательной проверкой: PR встанет
в вечное ожидание статуса, которого не будет.
